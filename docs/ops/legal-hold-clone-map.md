## Contract
These changes apply to legal-process holds (orders to the host). Explicit customer voluntary holds remain unchanged, as settled below.
- Preserve only order-covered stored material in a separate encrypted sealed legal hold store.
- Keep the user's ordinary vault normal. Erase, scrubs, compaction, and normal retention run there. Unerased originals keep their existing product behavior; a legal clone must never hide or retain the ordinary original.
- Permit clone storage, counsel review, legal search, and production only. Audit every access. Never feed the clone to product search, recall, Dreamer, training, sync, ordinary backup, or restore.
- Capture future stored material only when the order explicitly permits prospective capture, within its exact scope and term. Never begin recording content that the ordinary session keeps unwritten. Existing off-record disk spill is written scratch: an exact order covering that live session may preserve that already-written material.
- At release or expiry, stop capture and destroy that order's clone and keys, whether or not the user requested erase. Preserve only permitted content-free audit metadata.
- A pause of written scratch auto-deletion is temporary, exact-scope and term-bound, only until its ordered bytes have been preserved. It is not a whole-vault or whole-window pause.

## Storage and authority
One native legal-hold module owns order validation, capture manifests, immutable fingerprints, the legal access interface, and destruction state. Its content storage is separate from the ordinary vault's LMDB environment and body storage. No ordinary Vault or Store handle can be opened over a hold copy. No shared body-instance key, full-vault recovery key, ordinary checkpoint, or product index is needed to read the copy. The host must supply a real independently owned store/custody handle outside its ordinary vault backup/restore namespace. A different table in the same backed-up vault environment or a different directory scanned by its generic backup job is not separation.

Per-order custody owns fresh copy encryption keys. Bind each encrypted member to its order, source-vault identity, exact source identity/revision, and fingerprint. Use existing engine cryptographic primitives through L04's owning module; do not invent another encryption algorithm or use the existing sealed order-metadata member as a content store. Legal readers receive mediated review/production, not independently decryptable per-recipient key wraps that survive outside destroyable custody; every stored wrap/replica remains subject to that order's destruction. Fingerprints describe the exact ordered bytes and their immutable capture manifest. Appending an authorized prospective capture adds an immutable manifest revision; it does not rewrite an earlier fingerprint.

The host's legal access interface consumes an authenticated legal principal scoped to the order and action. An operator string, hosted posture, ordinary owner proof, or agent credential is not legal-read authorization. Legal list/review/search/production stays inside this interface. Commit an access event before making any plaintext or sensitive manifest visible; record outcome/completion separately. No plaintext release on an unaudited access. Do not log body text, key material, or legal query text into ordinary telemetry. Keep secrecy-order filtering for owner-visible metadata.

## Capture and mutation ordering
Placement and scope changes resolve actual existing stored versions through native family readers, not caller-supplied content or a list of raw IDs asserted complete. Copy only the ordered material and the exact native metadata needed to interpret and authenticate it. A dependency is not a reason to copy an unrelated body, a full carrier window, or a full backup. Fingerprint exact captured bytes and source revision identities, not a moving live selector. Keep content-derived fingerprints and source manifests in the legal-only store; ordinary logs receive only opaque capture references and status. AEAD context must be defined without a circular dependency on its own ciphertext/tag; L04 owns the canonical encoding and domain separation.

Linearize order attachment with ordinary writes and destructive maintenance. Pin the selected immutable bytes before releasing the source writer/snapshot. Seal and durably commit them into clone custody before reporting preservation complete or letting the last ordered source disappear. A cross-store handoff must have an idempotent durable capture record and crash recovery: a committed capture is never counted twice, a failed or partial seal never claims preservation, and recovery cannot resurrect content already released from custody. The same requirement covers prospective message commits: no acknowledged preservation may rely on a later best-effort callback or a promise that the next ingestion will cover a lost gap. Any deferred handoff must already own durable exact bytes independently of subsequent source deletion.

The mutation-owning writer completes the exact clone handoff before committing destruction of its last ordered source version. It must not acknowledge a complete erase on a failed copy. Return the actual storage/custody error through the existing mutation error path; do not translate it into “legal hold: delete refused”, an indefinite law-based pending erase, or a successful preservation/erase receipt. Recovery may retry that exact incomplete handoff, not retain an entire window or backup. This is the storage ordering required to make both preservation and erase true, not a new policy gate. Once the exact copy is durable, normal source erase and compaction must not wait for legal review, legal production, order expiry, or clone deletion.

## Order lifecycle
The native lifecycle distinguishes preparing a scoped copy, active preserved custody, stopping/destroying, and destroyed. These are custody facts, not new product admission states. Activation means the exact capture was durably sealed, not just a target index written. Scope widening adds an explicit capture revision; no hidden capture-all default. Order renewal changes its authorized term, not previously immutable fingerprints.

Every capture and legal access checks current order generation, scope, release state, and term at the point it commits/releases content. A caller-supplied message timestamp cannot extend the order. The admitted order names its exact time predicate; capture is disabled at its end even if a delayed message claims an earlier time. Renewal after destruction never revives an old key or copy. Already lawfully produced bytes cannot be recalled, but long-lived readers/streams must not release additional plaintext after their order ends. Expiry enforcement does not depend solely on a delayed housekeeper. Release first stops new capture/access, then invalidates outstanding owned work, destroys per-order unwrap paths and all copy-owned keys/ciphertext, and records completion only after those operations complete. Interrupted teardown remains durable cleanup work. Hold-specific replicas and recovery artifacts obey the same deletion, so restore cannot re-enable ended orders or recover their keys.

Overlapping orders own independent custody. Releasing one never destroys another order's still-authorized copy, but neither order retains unrelated ordinary-vault backups or keys. No cross-order deduplication that leaves hidden key access after release.
