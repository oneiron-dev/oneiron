# W8-T34 — recorded expiry clock

- Removed `AccessGrant::is_active` (process-clock read). Vault grant checks take one recorded `StoreClock` observation per evaluation; autonomy reuses its existing recorded `now` or clamped `at`. Pure grant predicates, the legacy consent projection adapter, and the cross-vault calendar projection require an explicit `now` from their caller.
- `AccessContext` retains a clone of the vault clock (sharing its monotonic floor). Load checks use one reading and `allows` takes a fresh reading, so a context kept beyond the expiry cannot reauthorize an old grant. A new context load is still needed for fresh membership/grant records.
- Kept `effective_status_at` status rules and consent-row `is_active` unchanged. The backwards-clock test relies on `StoreClock`'s monotonic floor; setting `ManualClock` back to 1900 cannot undo the earlier 2100 expiry. The forward test proves the injected clock drives expiry without wall-clock waiting.
- Canon: `site/src/pages/oneiron/agents/oneiron-arch-0060-event-ics-meetings-v1.astro` says the engine owns no timer. It is not wrong, but silent about grant expiry's clock source. Add a sentence that access-grant read-time expiry uses the vault's recorded clock and its monotonic floor, not the process clock.
