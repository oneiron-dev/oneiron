# W8-T33 implementation notes

- LFS streaming now stages anonymous upload files in `<vault>/lfs-staging`, created lazily at upload. The registered vault root owns the path; an unusable staging path returns the existing IO error.
- `max_lfs_object_bytes` is an optional server operator setting (TOML, `ONEIRON_MAX_LFS_OBJECT_BYTES`, `--max-lfs-object-bytes`) with no default. The server passes it to the engine upload door. The original engine stream API remains uncapped; the explicit capped variant checks each read before scanner/spool or ASSET writes and retains declaration, SHA-256, scanner, chunk and dedup checks.
- The existing `InvalidLfsObject` kind maps through the LFS route to a typed `BAD_REQUEST`; the reason names the configured object cap.
- Canon: `generated/oneiron/code-in-oneiron/oneiron-arch-0068-repo-custody-v1.md` (ARCH-0068 RA1, line 134 in the read-only docs mirror) rules vault-LFS BlobStore backing, chunked streaming, SHA-256 pointer identity; it does not set an LFS object cap. The mirror lacks registry row ONE-2592 and should add this ticket's optional operator cap and vault-owned spool rule. The phrase “no 16 MiB cap” concerns the prior fixed chunking rejection, not this optional cap. The former W7-C12 note against a fixed cap is superseded only for an explicit operator choice.
